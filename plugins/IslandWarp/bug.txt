一、必须修复（涉及钱、升级路径、性能基线）

A1.【计费静默丢失】退款/入账在"调度器拒绝执行任务"时既不执行、也不写人工处理日志
位置：
  - WarpEconomy.java:50-55  global()：Bukkit.getGlobalRegionScheduler().run(plugin, ...) 的返回值
    （TaskWrapper）没有判断。插件正在停用（或调度器拒绝任务）时 run 返回 null、任务不会执行，
    而这个 CompletableFuture 永远不会完成。
  - WarpEconomy.java:66-71  退款分支只在 refundError != null 时写"需人工退款"日志；future 永不完成
    时既没有日志、没有玩家提示，busy 锁也不会释放。
  - WarpEconomy.java:87-90  settle() 中 credit 的回调同样只在失败时记日志；future 永不完成时，
    门票收入既没入账、也不会写 income 记录、也没有任何日志。
  - WarpTeleport.java:66-69  退款用的是 credit(...).exceptionally(...)，同样是"只有失败才有日志"。
  - IslandWarpPlugin.java:43-47  onDisable 里 teleport.shutdown() 直接 pending.clear()，对"已扣款、
    还没开始传送"的请求不做任何退款或记录。
现象：停服/重载瞬间发生的付费操作，可能钱已扣、传送没发生、没有退款、日志里也没有"需人工处理"，
      玩家投诉时无从查证。
影响：低频但涉及金币，且事后无法补救。
建议（最小改动）：
  1) global() 里判断 null 返回值：
       var task = Bukkit.getGlobalRegionScheduler().run(plugin, t -> { ... });
       if (task == null) future.completeExceptionally(new IllegalStateException("插件正在停用，操作未执行"));
  2) 给退款/入账加超时兜底，超时按"需人工处理"记录：
       credit(id, cost).orTimeout(30, TimeUnit.SECONDS).whenComplete(...)
  3) onDisable 遍历 pending 时，若有已扣款状态（建议 Pending 里加个 paid 标记），至少写一条
     SEVERE 日志留下 UUID 与金额。
验证：【源码确认】调用链完整；【需实测】真实停服瞬间的扣款行为。
同理：WarpMenu.java:750-761（deliverNotices）在实体调度器返回 null 时不会执行也不执行 retired 回调，
      delivering 集合里会残留该 UUID，该玩家本次会话收不到聊天通知，建议 quit 时也 remove。

A2.【性能/扩展性】全量缓存刷新仍挂在热路径上：健康扫描每 5 秒一次、每次成功传送一次
位置：
  - WarpStore.java:129-198  refresh() = 约 14 条语句，其中 12 条是全表读取
    （warps/favorites/pins/tickets/ratings ×2/comments/replies/unread/notification_settings/
     warp_blocks/warp_status/warp_events），另外还顺手 UPDATE warps SET visible=0（读刷新里混写）。
  - WarpStore.java:219-226  每个 submit 提交后如 refreshCache=true 就全量刷新。
  - WarpStore.java:619-634  checked()（落点检测结果写入）走的是默认 refresh=true；
    而 WarpHealth.java:14-24 的定时扫描按 health.interval-seconds（默认 5 秒）检查一个坐标 →
    即"没人玩的时候也每 5 秒全量刷新一次"。
  - WarpStore.java:540-550  visit()（每次传送成功调用）也是 refresh=true → 每次传送一次全量刷新。
  - WarpStore.java:502-507  markRead()（每次打开留言板）refresh=true → 每次打开一次全量刷新。
  - WarpStore.java:756-774  remindPins()（每 60 秒）同样 refresh=true。
现状评估：数据量小时无感；岛服规模（几千地标、几万留言）时，refresh 的耗时 × 每分钟十几次，
          会让单线程数据库队列出现可见积压，表现为"点按钮要等"。上一轮已指出方向，本轮只剩热路径。
建议（任选，越小越好）：
  1) 对"只影响单条记录"的写入改为增量发布快照，例如：
       // checked()
       Map<Long,Status> next = new HashMap<>(statuses); next.put(id, newStatus); statuses = Map.copyOf(next);
       // visit()
       Map<Long,Warp> next = new HashMap<>(warps);
       Warp old = next.get(id); if (old != null) next.put(id, old.withVisits(old.visits()+1));
       warps = Map.copyOf(next);
     （需要给 Warp 加一个 withVisits 小方法；与现有"提交成功后才发布快照"的原则一致。）
  2) 或把 refresh() 参数化成"只刷新受影响的表"，让 visit/checked/markRead 只刷新 warps/statuses/unread。
  3) 或加合并刷新：置脏标记，最多每 N 毫秒最多刷一次。
动手前建议先量一次：用接近正式服的数据量（例如 2000 地标 / 20000 留言）打印一次 refresh 的耗时，
否则改完无法判断效果。
验证：【源码确认】调用链与触发频率。

A3.【配置语义】economy.enabled=false 时无法设置门票价格
位置：WarpEconomy.java:15-20（cost() 在 economy.enabled=false 时直接 return 0）、WarpCommand.java:165。
现象：关掉收费总开关后，`/iw ticket <id> price 50` 报"票价超出允许范围"——因为 max-ticket 被当成
      "要收的金额"读取，而开关关闭时它恒为 0。
影响：经济暂时关闭（维护中）时无法预置票价；重开后又忘了，运营上会踩。
建议：max-ticket 作为"上限"独立读取，不要经过 cost()，例如
      double max = plugin.getConfig().getDouble("economy.max-ticket", 10000);
      if (!Double.isFinite(max) || max < 0) throw new IllegalArgumentException("经济配置金额无效");
      if (price > max) throw ...
顺带：economy.enabled=false 时，创建/购买推荐位仍会弹出"0.00 金币"的付款确认页
      （WarpCommand.java:105、WarpMenu.java:783），可以直接跳过确认少点一次。
验证：【源码确认】。

A4.【升级路径】recycle_* 镜像表不跟随主表结构变化，旧库升级后删除/恢复会直接报 SQL 错
位置：
  - WarpStore.java:107  CREATE TABLE IF NOT EXISTS recycle_x AS SELECT *,0 AS trash_warp FROM x WHERE 0
    （镜像表只在"该库第一次运行带回收站的版本"时定型）
  - WarpStore.java:286-289  删除时 INSERT INTO recycle_x SELECT *,? FROM x WHERE ...（无列名列表）
  - WarpStore.java:336-342  恢复时按主表 PRAGMA table_info 生成列名，再从镜像表取同名列
问题：主表加列后（本项目已经发生过一次：WarpStore.java:101-103 给 comments 加了 edited），
      旧库的 recycle_comments 仍是旧列数：
      - 删除：SQLite 报 "table recycle_comments has 7 columns but 8 values were supplied"
        → 整个 delete 事务失败（数据不丢，但该库的删除功能永久坏掉，玩家只能看到"操作失败"）。
      - 恢复：报 "no such column: edited" → 旧回收记录也恢复不了。
建议：构造 WarpStore 时对每个 RECYCLED 表做一次结构对齐：比较 PRAGMA table_info(主表) 与镜像表的
      列集合，缺列就 ALTER TABLE recycle_x ADD COLUMN ...（保留旧回收数据）。
      并补一条回归检查：手工造一个只有旧列的 recycle_comments，然后跑 delete/restore。
验证：【源码确认】；【需实测】用旧版本生成的库跑一次 delete/restore。

二、建议修复（功能性小 Bug 与配置语义）

B1. 坐标 lore 里的"世界"显示成世界 UUID
    位置：WarpMenu.java:160-164（{world} 用的是 w.world()，而 Warp.world 是 UUID）；
          配置示例在 config.yml:70-73（'&7世界 &f{world}'）。
    现象：玩家看到"世界 3f8b0e2c-....-...."，不是 world / world_nether。
    建议：Bukkit.getWorld(w.world()) 取名字，世界未加载时回退为"未加载"（顺便别把 UUID 露给玩家）。

B2. admin.manage-player-warps 只在 GUI 生效，命令仍可绕过
    位置：配置 config.yml:104；GUI 判断在 WarpMenu.java:402、411；
          命令侧 WarpCommand.java:154(edit)、153(delete→WarpMenu.confirm:842)、155(ticket)、82(event)
          都只判断 islandwarp.admin，不读这个开关。
    影响：把它设为 false 的服主以为管理员不能再动玩家坐标，实际还能改/删/改票价/设活动。
    建议：要么在 WarpStore 的写入口统一校验（更安全），要么在配置注释里写清"仅限制界面操作"。
    附带：admin.panel-enabled=false 会把 /iw admin pin|freeze|unfreeze|export 一起禁掉
          （WarpCommand.java:34-35 的判断在子命令分派之前），而注释只说"关闭管理面板"。确认是否有意。

B3. find() 把"名称"和"ID"放在同一个流里按顺序匹配，数字名字可以遮挡别人的 ID 查找
    位置：WarpCommand.java:175-178
      .filter(w -> Long.toString(w.id()).equals(text) || WarpText.plain(w.name()).equalsIgnoreCase(...))
    现象：任何人可以把自己的坐标命名为 "42"。此后 /iw tp|detail|edit|delete|ticket|event|favorite
          42 命中的是"名字为 42 的坐标"还是"ID=42 的坐标"，取决于 store.all() 这个不可变 map 的遍历
          顺序（未定义），也就是随机；ID=42 的坐标可能在自己的服里"打不开"。
          另外管理员命令 /iw admin freeze 42 用的是 Long.parseLong（真 ID），与玩家命令行为不一致。
    建议：先单独找 ID（Long.toString 匹配且命中唯一），命中就直接返回；否则再按名称找。
    名称允许纯数字是否合理也可以顺带定一下（WarpText.name 目前允许）。

B4. 永久置顶（expires=0）仍显示"续费置顶"按钮，点了一定报错
    位置：WarpMenu.java:796（只要含有该地标的置顶位且 renew-enabled 就画按钮）、
          WarpMenu.java:698-711（renew() 对 expiry<=now 直接抛"永久置顶无需续费"）。
    影响：管理员置顶的坐标（永久）和 featured.duration-days=0 的服，玩家点续费必然失败，像坏按钮。
    建议：按钮条件加上 plugin.store.pinExpiry(slot)>0。

B5. featured.slots<7 时，首页仍固定画 7 个置顶位
    位置：WarpMenu.java:281-285（for(i=0..6)，只有 i<featuredSlots() 才画真实卡片，否则画"空闲"）。
    现象：slots=3 时，首页多出 4 个"置顶位 4-7 · 空闲"，但购买/管理员置顶都拒绝 >slots 的位置，
          永远不会被填上。
    建议：循环上限改为 featuredSlots()。
    附带：已置顶但被隐藏/不可用的位也会显示成"空闲"，与"这里被占用"的事实不符，可考虑换文案。

B6. ratings.enabled=false 时，列表仍按评分排序
    位置：WarpMenu.java:259 只读了 ratings.sort-by-rating 与 ratings.min-count，没读 ratings.enabled。
    影响：关掉评分后，历史评分仍长期影响排序（并且卡片上还在显示评分），与开关预期不符。
    建议：排序条件里加上 ratings.enabled；或明确注释"关闭只隐藏评价入口，不影响排序"。

B7. 玩家文本里的颜色代码会进入 GUI，theme() 还会覆盖玩家的颜色
    位置：WarpMenu.java:110-114（theme 把 &b/&a/&c 一律替换成配置色）、
          WarpMenu.java:104-106（名称与 lore 用 legacyAmpersand 渲染）、
          WarpText.java:19-20（plain/normalize）、WarpStore.java:480-482（validateText 只查长度/空/换行）。
    现象：留言、描述、坐标名里写 &l、&k、&o 会被当成格式代码渲染进图标名和描述，玩家可以用 &k
          把 GUI 文案搅乱；反过来，玩家想用 &b/&a/&c 又会被人为改成强调色。
    建议：展示玩家文本时统一用 PlainTextComponentSerializer 或先剥掉格式代码（只保留默认样式），
          theme() 只作用于插件自己的文案。

B8. 配置里有几个键实际不会被读到
    位置：config.yml:51 clear-search、config.yml:68 edit、config.yml:69 back（全项目没有 material("clear-search")/
          material("edit")/material("back") 的调用）；
          config.yml:42 注释里列出的头颅键 browse/help/reset（代码只用 previous/next/my-warps/create/delete）。
          README.md:14 还描述了"清除搜索保留分类、重置全部筛选清除关键词和分类"两个按钮，
          当前界面只有一个"重置搜索"（WarpMenu.java:278）。
    建议：删掉无用键（或补上实现），并修正 README/注释。

B9. ConfigCheck 依赖工作目录 + 做字节级比较，容易误报或漏报
    位置：verification/ConfigCheck.java:17-19（Path.of("src/main/resources/config.yml")、
          Path.of("配置参考.yml")、Files.readAllBytes 全等比较）；pom.xml:15-23 的 antrun 用相对路径调用。
    问题：1) `mvn -f D:\...\pom.xml test` 从别的目录执行时，相对路径找不到文件 → 检查直接失败；
          2) 字节全等对换行符（CRLF/LF）、BOM、编码敏感，换一台机器或换编辑器就会误报；
          3) 中文文件名在部分 CI/打包链路上不可靠。
    建议：把 ${basedir} 通过 -D 传给检查程序，改成"解析后的 YAML 深度比较"，忽略换行与编码差异。

B10. 落点支撑判定用 isSolid()，会拒绝地毯/雪层等合法落脚点
    位置：WarpTeleport.java:98-105（floor.getType().isSolid()）。
    现象：站在地毯、雪层、睡莲一类"可踩但不 solid"的方块上时，创建与传送都会被判"落点不安全"，
          只能提示"请联系岛主更新位置"。
    建议：若这是有意的保守策略，可在配置注释里说明；否则改为"有碰撞箱即可"，例如
          !floor.isPassable() && !floor.isEmpty()（同时仍保留危险方块、边界、头顶空间的判定）。

B11. shared / delivering 退出时不清理
    位置：WarpMenu.java:886（quit 只清 inputs/views/filters）、WarpMenu.java:24、741。
    影响：小内存泄漏；delivering 里残留的 UUID 会让该玩家本次会话收不到聊天通知（需重新登录）。
    建议：quit 里一并 remove（shared.remove、delivering.remove）。
    附带：分享冷却只存内存，重连即清零（传送冷却已改成重连保留），两者行为不一致，建议统一。

B12. teleport.delay-seconds=0 实际仍会等 1 tick
    位置：WarpTeleport.java:29（Math.max(1, seconds*20L)）；config.yml:13 写的是"0 为立即传送"。
    现象：差异只有 50ms，玩家无感，但和文档描述不符。
    建议：改成 Math.max(0, ...)，或把注释改成"0 为下个 tick 传送"。

三、长期数据增长（不用立刻改，但建议定保留策略）

C1. daily_visits：每个坐标每天一行，永久保留（WarpStore.java:546），而界面只读最近 30 天
    （WarpStore.java:737-744）。几千坐标 × 几年 = 几十万～上百万行。
    建议：visit 或定时任务里删除 90 天前的行。
C2. income：每次成功付费传送一行（WarpStore.java:361-368），无上限；界面分页列出全部。
    建议：加保留期或按月聚合。
C3. notices：只有 acknowledge 才删除（WarpStore.java:508-516）。玩家长期屏蔽聊天提醒时
    notices 一直堆积（notices() 直接返回空但不清理），解除屏蔽后会一次性刷屏。
    建议：给每个玩家保留上限，或屏蔽期间直接丢弃（历史仍保留在 notice_history，不影响通知中心）。

四、小问题 / 清理（可选，不影响功能）

D1. 纯读操作也走了 setAutoCommit(false)+commit（WarpStore.java:203-210），可以直接跳过事务。
D2. submit(task,false) 是维护陷阱：以后给"有缓存"的表加写操作时忘了刷新，缓存会静默不一致。
    建议改名为 submitWrite/submitRead，或在写入分支断言 refreshCache。

【7.2-1 必须修 · 涉及钱】门票结算失败会让访客被"未完成交易"长期挡住
  位置：WarpTeleport.java:87、WarpEconomy.java:110-119、WarpStore.java:422-424
  现象：传送成功后调用
