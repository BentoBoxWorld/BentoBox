IslandWarp 插件代码审查汇总
审查日期：2026-10-12
审查范围：源码、构建配置、配置模板、verification 检查程序及已有测试服日志。
预期场景：Folia/Lophine 单服，几十至几百名在线玩家，多人同时访问热门地标，数据长期累积。未做该规模的实服压测。

一、总体评价

综合评价：中等偏上，约 7/10。有工程意识，超过简单功能拼接，但上线收费运营前仍需修复关键问题。

优点：
1. SQLite 使用专用线程串行执行，启用 WAL、外键和事务。
2. 界面与存储层都有权限检查，传送前多次复查权限、岛屿状态和票价。
3. 使用实体调度器、区域调度器、异步区块加载和 teleportAsync，考虑了 Folia 的线程要求。
4. SQL 大多使用参数绑定，CSV 导出处理了公式注入。
5. 回归检查覆盖越权、重启持久化、关联清理、退款、回收站等，并明确披露模拟测试的限制。

主要短板：并发状态判断、数据库提交后的错误处理、数据增长后的性能，以及测试与文档的持续维护。

二、必须修复

1. 数据库已提交，却仍返回失败，可能触发错误退款

位置：
- src/main/java/com/islandwarp/WarpStore.java:201-213
- src/main/java/com/islandwarp/WarpEconomy.java:63-70

问题：
submit() 先 commit，再 refresh，两步共用同一个异常处理。
如果提交成功后缓存刷新失败，Future 仍返回失败。此时 rollback 无法撤销已提交的数据，但经济层会按保存失败申请退款。

影响：
异常情况下，创建或购买操作可能已经保存，却退还了费用；调用方看到失败，数据库里却已经成功。

建议：
明确区分“事务写入失败”和“提交成功但缓存刷新失败”。后一种情况应记录故障并修复缓存，不能向付款层返回可退款的保存失败。

验证情况：
已在隔离临时数据库注入缓存刷新故障，复现“操作返回失败，但写入已提交”。错误退款后果由经济层调用链确认，未在真实 Vault/CMI 环境复现。

2. 其他玩家访问成功，会让正在进行的传送误判为地标被修改

位置：
- src/main/java/com/islandwarp/WarpTeleport.java:58、73
- src/main/java/com/islandwarp/WarpMenu.java:207
- src/main/java/com/islandwarp/WarpStore.java:607
- src/main/java/com/islandwarp/Warp.java:5-7

问题：
传送、预检查和健康检查使用整个 Warp.equals() 判断地标是否变化，而 Warp 包含 visits 访问次数。
玩家 A 成功访问并增加计数后，玩家 B 正在进行的传送可能被判定为“地标发生变更”，即使坐标、公开状态和权限都没有变化。

影响：
热门地标多人同时访问时可能出现无意义的取消、退款或检测失败。

建议：
只比较影响当前操作的字段，排除访问计数等统计字段；保留票价、冻结、活动和权限的独立复查。

验证情况：
已验证仅 visits 变化就会使 Warp.equals() 返回 false。实服多人同时传送的端到端复现尚未执行。

三、应该修复

3. 每次数据库操作都全量刷新缓存，长期运行容易积压

位置：
- src/main/java/com/islandwarp/WarpStore.java:127-198、207
- src/main/java/com/islandwarp/WarpMenu.java:35-43

问题：
所有 submit() 完成后都重新读取地标、收藏、评分、留言、回复、未读、黑名单等缓存。
查收入、查通知、确认通知已投递等操作也会全量刷新。每分钟还会对在线玩家查询通知，工作量随数据量和在线人数增长。

影响：
数据库使用单线程队列，积压会拖慢创建、收藏、留言和收费操作。

建议：
先将不改变缓存的查询与写入区分，让纯查询跳过 refresh；再根据测量结果优化需要更新的缓存。

验证情况：
已确认调用链和全量读取行为；未进行负载测试，不能据此给出具体人数或数据容量上限。

4. 传送冷却可以通过重新登录绕过

位置：
- src/main/java/com/islandwarp/WarpTeleport.java:133

问题：
PlayerQuitEvent 同时删除待传送请求和冷却记录，玩家传送成功后退出再登录，尚未结束的冷却会消失。

影响：
配置的冷却限制无法对重连玩家生效。

建议：
退出时清理待传送请求，保留未到期冷却，并清理过期记录。

验证情况：
由源码直接确认；未做真人重连测试。

5. 现有检查程序没有接入标准构建流程

位置：
- pom.xml:13-16
- verification/*.java

问题：
检查程序放在 verification，需要单独编译运行。mvn test 不会运行这些检查，本次 Maven 明确输出“No tests to run”。

影响：
后续改动只看构建成功，容易漏掉回归。

建议：
提供统一验证入口并接入构建或 CI；补充问题 1、2 的回归检查。

验证情况：
已确认 Maven 不执行检查；本次手动编译并执行 9 个已有检查程序，全部通过。

6. 配置和文档与实现不一致

位置：
- src/main/resources/config.yml:85-90
- src/main/java/com/islandwarp/WarpMenu.java:397-403
- src/main/java/com/islandwarp/WarpStore.java:365-374
- README.md:66
- 配置参考.yml:64

问题：
配置提供 ratings.min-stars、ratings.max-stars，但界面和存储固定使用 1-5 星。
README 仍写“没有评分”，根目录参考配置仍描述五个永久推荐位，与当前实现不符。

影响：
服主修改评分上下限不会生效，旧说明也可能误导推荐位的部署和使用。

建议：
若评分固定为 1-5 星，删除无效配置；同步 README 和配置参考，保留一个权威配置模板。

验证情况：
已搜索并核对配置、源码和文档。

四、可顺手清理
